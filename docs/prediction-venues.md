# Prediction venue integration

Kalshi and Polymarket US are separate venue adapters that feed NOEMA's existing immutable market snapshot and forecast ledger. Kalshi production is used for current read-only market and account observation. Production order authority remains off unless the existing explicit owner settings are enabled; this integration does not enable them. Polymarket US public discovery uses the official `polymarket-us` SDK, and current public quotes are recorded as market benchmarks in the same forecast ledger.

Kalshi credentials are loaded from macOS Keychain service `com.noema.kalshi.key-id` (account `noema-owner`) and the owner-only file `~/.config/noema/credentials/kalshi.pem`. The PEM is not copied. Polymarket US uses the official SDK's Key ID and Secret Key, stored separately in Keychain services `com.noema.polymarket-us.key-id` and `com.noema.polymarket-us.secret-key` (account `noema-owner`). Neither value is emitted to runtime status or the workstation.

`GET /api/prediction-venues` performs cached read-only health checks for public market discovery, one current quote/book per venue, and authenticated account state where credentials exist. The Home view labels a same-outcome candidate separately from an executable opportunity. It does not infer arbitrage from a raw price difference when settlement rules, fees, or depth are unknown.

Cross-venue identity is represented as separate levels: topic, event, proposition, outcome, semantic match, settlement equivalence, economic comparability, and executable comparability. The live production cross-venue probes currently verify two structurally different families: MLB championship winner and Tesla Q3 delivery numeric threshold. The API separately reports six ontology shapes: winner, occurrence-by-deadline, numeric threshold, numeric bucket/range, asset price at a timestamp, and economic-release bucket. Strict source adapters also identify Kalshi's observed NYC rainfall occurrence and ETH timestamped price propositions, but no exact Polymarket US counterpart is registered for either. The current BTC range remains unresolved because endpoint inclusion is ambiguous in its rule text; no economic-release bucket resolver is registered. These statuses do not imply a live overlap. `identify_explicit_proposition` does not parse titles or use fuzzy similarity; missing or ambiguous fields remain unresolved.

Each real pair observation is appended to `canonical_pair_observations` and materialized into the forecast database's canonical event/proposition projections, venue-contract links, append-only contract observations, identity assessments, settlement assessments, economic-comparability assessments, and quote observations. New settlement assessments are append-only: a rule update can add a mismatch or unverified assessment and revoke a previous confirmation without rewriting prior evidence. Rule-text hashes are references, not proof that resolution outcomes are equivalent. The normalized rule comparison covers resolution and measurement sources, cutoff and timezone, preliminary/final data, revisions, cancellation, postponement/rescheduling, ties, rounding, exceptional conditions, expiration, and disputes. Both live pairs lack enough extracted paired fields to confirm settlement equivalence, so they remain unverified.

Economic comparability carries fee model, denomination, bid/ask, quote time and age, available depth, minimum and maximum size, expected slippage, and capital lock. The current read-only feeds do not provide verified values for every required field (including venue quote timestamps and consistent usable depth), so the live pair stays economically unavailable and executable comparability unavailable. A shared economic-event DTO sends persisted canonical observation provenance to NOEMA's existing `EconomicLedger`; this module does not create its own money accounting.

The slow identity path discovers candidates and resolves canonical links. The fast path refreshes quotes for already registered pairs without rerunning identity resolution; periodic slow re-review remains necessary for revoking identity/settlement claims after venue rule changes. The bounded production candidate path currently probes only MLB championship winner and Tesla Q3 delivery thresholds; it is not a full-catalog matcher. Similar-looking live Kalshi and Polymarket US markets in other structures are intentionally unresolved until an official-schema mapping establishes identical event, boundary, benchmark, timestamp, and outcome semantics.

At the 2026-09-29 live read-only check, `KXMLB-26-MIL` and `tec-mlb-champ-2026-09-27-mil` resolved to the same Milwaukee 2026 baseball championship outcome. `KXTSLA-26OCTDELIV-440000` and `kpic-tsla-dlvrs-2026-q3-above-440k` resolved to the same Tesla Q3 deliveries threshold. `KXRAIN-26SEP29-NYC` and `KXETH-26SEP2901-T1905` were source-mapped to distinct occurrence-by-deadline and asset-price-at-time identities, with no verified Polymarket US counterparts. The `KXBTC` range contract remains unresolved because the primary rule uses “between” without an endpoint convention. Polymarket US BTC-touch markets and annual Fed-rate-cut propositions are not equivalent to a timestamped price or meeting-specific rate threshold. These are live catalog observations, not fuzzy title mappings.

Official schema references consulted for this pass: [Kalshi events and nested markets](https://docs.kalshi.com/api-reference/events/get-multivariate-events) expose structured rules, price ranges/strikes, expirations, timestamps, and quote/depth fields; [Polymarket US read-only data guide](https://docs.polymarket.us/data-guide/overview) documents instruments/metadata, BBO, L2, and streaming data, while the current market adapter returns venue-specific description and end-date fields. These schemas are not interchangeable and raw text is not sufficient for semantic equivalence.

This pass does not place orders. Kalshi already has a venue-specific executor behind the pre-existing deterministic gates. Polymarket US order creation, fill/settlement reconciliation, fee accounting, streaming-book verification, executable-depth modeling, paper paired fills, and promotion into live execution are not enabled by the read-only adapter and require their own verified integration before any order path is exposed.
