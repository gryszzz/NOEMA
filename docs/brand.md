# NOEMA Brand

## Name

**NOEMA**

A noema is an object/content of thought. The name fits a system whose job is to form explicit, calibrated beliefs about uncertain events.

## Core line

> **Observe. Infer. Verify. Act.**

Alternative internal line:

> **Evidence → Belief → Edge → Restraint**

## Product personality

NOEMA should feel:

- precise;
- immersive and spatial;
- technical;
- dark, futuristic and interactive;
- evidence-first;
- game-like without casino cues;
- adaptive rather than mystical;
- powerful because it rejects bad opportunities.

It should not look like:

- a casino;
- a meme-coin terminal;
- a "guaranteed profit" bot;
- an LLM chat wrapper.

## Visual language

Preferred UI:

- black / near-black background;
- slate panels;
- thin technical borders and deliberate depth;
- electric blue and cyan for information and connected capabilities;
- violet for specialist and research object types;
- green for verified/healthy;
- amber for uncertainty;
- red for hard failures;
- monospace numeric surfaces.

The operating console can feel like a future agent-economy field: interactive,
spatial and game-like, with clear economic dashboards and research progress.
Depth, emphasis and progress must remain attached to a real node, persisted
event, measured allocation or reported outcome. A settled paper P&L chart must
say it is hypothetical; it does not stand in for verified revenue or profit.

## Information hierarchy

The console should always distinguish:

1. **Observed** — exchange/API facts.
2. **Derived** — deterministic calculations.
3. **Model** — probabilistic estimates.
4. **Research** — unproven diagnostic features.
5. **Action** — what passed deterministic policy.

Never render a research score with the same visual authority as an observed exchange fact.

## Identity assets

- [Wide repository banner](../noema/static/brand/noema-banner.png) — NOEMA wordmark,
  core line, and the observing face. Use it as a README cover or wide header.
- [Square face mark](../noema/static/brand/noema-face.png) — avatar and profile image.

The face is a visual identity, not a claim of personhood or independent legal
agency. Keep the language plain: **NOEMA** is a research system with clear
owners, data sources and operating limits.

Core colors: near-black navy, slate, electric blue, cyan/teal, violet for object
types, and a restrained amber point for uncertainty. Product status must continue
to distinguish observations, models, research and action. Do not use the face to
imply live trading is active.

## Capability graph and UI transformation brief

The UI must make NOEMA's real intelligence and capability graph visible as a
living system, not just list data. Reflect real capability and agency, not
decoration. Every visual element must map to real NOEMA state; every glow is
earned.

Surface the live capability graph so NOEMA's UI shows connected providers,
wallets, sub-agents and tools as real nodes, not static text. Represent each
agent, wallet, provider and tool as a first-class object in a simple internal
capability-graph model. A node's identity, type metadata, status, capabilities
and limits must come from current application state or explicitly persisted
records. Keep unknown or stale state unknown or stale; never imply a connection,
permission or ability that the system has not observed. Show meaningful states
such as read-only, degraded, offline and execution disabled. Interactions can
reveal what a node can do and what it cannot do, including the evidence and
freshness behind its status.

Only animate or highlight nodes and links in response to real state changes or
recorded events. A displayed link must represent a real configured or observed
relationship, not an illustrative connection. The graph describes capability;
it does not grant authority. Live execution remains disabled unless the
independent deterministic policy, explicit owner authorization, supported venue
adapter and other execution prerequisites all permit it.

Use real 3D only where spatial relationships make intelligence easier to
understand. Three.js Journey, React Three Fiber documentation and examples,
PMNDRS Drei and Theatre.js are implementation references for 3D and motion;
PixiJS is an option when 2D is clearer. Treat these as tools, not a style guide.
Use GLB assets only when needed, and choose assets with open licenses from
sources such as Poly Haven or AmbientCG. A clear, accessible 2D graph is better
than a 3D demo that obscures state, interactions or limits.
